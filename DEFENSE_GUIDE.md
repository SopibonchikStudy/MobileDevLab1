# Punchline — описание проекта для защиты

> Этот документ объясняет устройство приложения по фактическому коду: что
> сделано, как связаны компоненты, где хранятся данные, что показывать на защите
> и как отвечать на вероятные вопросы. Он дополняет запуск приложения, но не
> заменяет демонстрацию.

## 1. Краткое представление проекта

**Punchline** — Android-приложение для локально авторизованного пользователя,
которое получает коллекцию шуток из JokeAPI, сохраняет её в кэш и позволяет
создать автономную резервную копию. Проект демонстрирует четыре отдельные
Activity, переходы между ними, валидацию, работу с сетью и файлами, Jetpack
Compose, Material Design 3 и журналирование жизненного цикла.

Формулировка для защиты:

> «Punchline — мобильная коллекция шуток. Пользователь регистрируется локально,
> входит и получает от 12 до 20 уникальных шуток JokeAPI. Лента кэшируется,
> поэтому ранее загруженные данные доступны без сети. В настройках можно
> изменить профиль, оформление и язык, а также создать, восстановить или удалить
> JSON-копию коллекции. Каждый экран реализован отдельной Activity, а жизненный
> цикл всех Activity журналируется единым механизмом».

## 2. Запуск и проверка

```bash
./gradlew assembleDebug
```

APK создаётся здесь:

```text
app/build/outputs/apk/debug/app-debug.apk
```

Установка на подключённое устройство или эмулятор:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Для сценария первого запуска можно очистить данные тестового приложения:

```bash
adb shell pm clear com.example.a1lab
```

Эта команда удаляет локальный аккаунт, настройки, кэш и резервную копию,
поэтому её следует применять только на тестовом устройстве.

Unit- и instrumentation-тесты из проекта удалены по требованию минимальной
конфигурации. На защите не следует называть `./gradlew test` текущей проверкой
проекта: сборка подтверждается `assembleDebug`, а поведение — ручными сценариями.

## 4. Архитектура и поток данных

Используется прагматичный MVVM с однонаправленным потоком данных:

```text
Пользовательское действие
        ↓
Compose-экран передаёт событие ViewModel
        ↓
ViewModel вызывает репозиторий
        ↓
Репозиторий работает с API, SharedPreferences или файлами
        ↓
ViewModel обновляет MutableStateFlow
        ↓
Activity собирает StateFlow через collectAsStateWithLifecycle()
        ↓
Compose отображает новое неизменяемое состояние
```

Постоянное состояние представлено `StateFlow`. Одноразовые сообщения, например
«Копия создана» или «Не удалось загрузить шутки», передаются через буферизованный
`Channel`. Это не позволяет Snackbar повториться после реконфигурации экрана.

Activity не выполняет HTTP-запросы, не разбирает JSON и не работает с файлами.
Это ответственность data-слоя. Domain-слой не зависит от Android UI, Compose,
HTTP или `JSONObject`.

### Сборка зависимостей

`PunchlineApplication` создаёт один `AppContainer` при старте процесса.
Контейнер содержит интерфейсы `UserRepository`, `SettingsRepository`,
`JokeRepository` и `BackupRepository`. Activity получают ViewModel через
фабрику и передают ей зависимости из контейнера.

Ручной DI выбран потому, что приложение небольшое, а явные конструкторы проще
для понимания и замены реализаций на фейки.

## 5. Четыре Activity

| Activity | Экран | ViewModel | Основные действия |
|---|---|---|---|
| `StartActivity` | Бренд и вход | `StartViewModel` | Вход, запуск регистрации |
| `RegistrationActivity` | Регистрация | `RegistrationViewModel` | Создание аккаунта |
| `ContentActivity` | Коллекция шуток | `ContentViewModel` | Загрузка, обновление, восстановление |
| `SettingsActivity` | Настройки | `SettingsViewModel` | Профиль, оформление, копия |

Все четыре Activity наследуют `LoggedActivity` и используют Compose через
`setContent`. Только `StartActivity` имеет intent-filter `MAIN`/`LAUNCHER` и
`android:exported="true"`. Остальные Activity не экспортируются наружу.

## 6. Навигация

```text
StartActivity
    ├── «Создать аккаунт» → RegistrationActivity
    │                            │ RESULT_OK(login)
    │                            ▼
    │                        StartActivity
    │
    └── успешный вход → ContentActivity [StartActivity.finish()]
                              │
                              └── «Настройки» → SettingsActivity
                                                      │ RESULT_OK
                                                      ▼
                                                  ContentActivity
```

### Регистрация

`RegistrationContract` реализует `ActivityResultContract<Unit, String?>`.
`RegistrationActivity` возвращает только логин. После `RESULT_OK`
`StartViewModel.onRegistrationReturned()` предзаполняет логин и обновляет
приветствие. Пароль, соль и хеш через `Intent` не передаются.

### Вход

После успешной проверки логина и пароля `StartViewModel` отправляет
`StartEvent.Authenticated(login)`. `StartActivity` открывает
`ContentActivity`, передаёт только логин и вызывает `finish()`, поэтому
стартовый экран не остаётся в стеке. Флаг `navigating` предотвращает обработку
повторного навигационного события.

### Настройки

`SettingsContract` возвращает логин и признак изменения профиля.
`SettingsActivity` передаёт результат через `setResult(RESULT_OK, ...)` и
закрывается. Системная кнопка «Назад» и кнопка toolbar вызывают один метод
`returnToContent()`. Из настроек пользователь возвращается только к коллекции.

## 7. Авторизация и пароль

Стартовый экран показывает логотип и название Punchline, описание, состояние
первого или повторного входа, поля логина и пароля, кнопки входа и регистрации.
После повторного запуска профиль читается из `SharedPreferences`, поэтому
отображаются приветствие и сохранённый логин.

`PasswordHasher`:

1. создаёт 16-байтовую случайную соль через `SecureRandom`;
2. формирует ключ из пароля;
3. выполняет итеративное HMAC-SHA256-преобразование;
4. сохраняет отдельно Base64-соль и Base64-хеш;
5. сравнивает хеши за постоянное время;
6. затирает массивы пароля и промежуточные байты после использования.

Количество итераций — 20 000. Это учебная реализация salted HMAC-SHA256,
удовлетворяющая варианту из требований. Для production лучше использовать
проверенную библиотеку PBKDF2 или Argon2 с рекомендованными параметрами.

Через `Intent` передаётся только логин. Пароль, соль и хеш не попадают в `Intent`
и Logcat.

## 8. Регистрация и валидация

Поля регистрации: имя, логин/e-mail, возраст, пароль и подтверждение.

| Поле | Правило |
|---|---|
| Имя | от 2 до 40 символов после `trim()` |
| Логин/e-mail | от 3 до 64 символов; при наличии `@` проверяется формат |
| Пароль | от 6 до 64 символов |
| Подтверждение | совпадает с паролем |
| Возраст | необязателен; если указан, целое число от 6 до 120 |

Ошибка возвращается как `ValidationError`, а не как строка внутри domain-слоя.
Экран превращает ключ ошибки в локализованный текст. Ошибки отображаются рядом с
полями, результат операции — через Snackbar.

В настройках имя и возраст проверяются тем же валидатором, поэтому правила
нельзя обойти через второй экран.

## 9. Работа с JokeAPI

Endpoint:

```text
https://v2.jokeapi.dev/joke/Any
```

Параметры:

```text
type=twopart&amount=10&safe-mode&lang=en
```

`RemoteJokeRepository`:

1. выполняет запрос в `Dispatchers.IO`;
2. устанавливает `connectTimeout` 10 секунд и `readTimeout` 15 секунд;
3. проверяет HTTP-статус до чтения тела;
4. читает ответ в UTF-8;
5. передаёт JSON в `JokeJsonCodec`;
6. выполняет до трёх запросов по 10 шуток;
7. удаляет дубликаты по `id`;
8. требует минимум 12 уникальных шуток;
9. ограничивает результат 20 шутками;
10. атомарно сохраняет успешный результат в кэш;
11. закрывает соединение в `finally`.

Если API вернул ошибку или меньше 12 уникальных шуток, новый кэш не записывается.
Существующий кэш при этом не стирается.

`HttpURLConnection` выбран потому, что контракт JokeAPI простой, а библиотека
входит в Android SDK и не увеличивает APK. Для большого API с авторизацией и
сложной сериализацией разумнее были бы Retrofit и OkHttp.

`JokeJsonCodec` проверяет `error: true` и `message`, поддерживает массив или
одиночный ответ, преобразует `setup`/`joke` и `delivery` в доменную модель,
обрабатывает неизвестные категории и считает слова. В Compose передаётся
`JokeCard`, а не `JSONObject` или сырой ответ API.

## 10. Экран коллекции

`ContentActivity` получает `ContentUiState` из `ContentViewModel` и показывает:

- индикатор первой загрузки;
- отдельное состояние ошибки с кнопкой повтора;
- пустое состояние с возможностью восстановить копию;
- `LazyColumn` с карточками, используя API `id` как стабильный ключ;
- кнопку обновления;
- кнопку перехода в настройки.

В каждой карточке есть текст шутки или вопрос, панчлайн при наличии, категория,
тип `single`/`twopart`, количество слов и графический бейдж категории с
текстовым `contentDescription`. Для `single`-шутки пустой блок панчлайна не
отображается.

## 11. Кэш и офлайн-режим

Кэш находится в `filesDir/jokes_cache.json`:

```json
{
  "version": 2,
  "source": "https://jokeapi.dev/",
  "jokes": []
}
```

Фактический массив содержит шутки; здесь он сокращён. Флаг инициализации
хранится в `SharedPreferences` `joke_cache_state`.

Логика `getJokes()`:

- при первом обращении без инициализации выполняется сетевая загрузка;
- при наличии кэша он читается без обязательного сетевого запроса;
- после явной очистки возвращается пустая коллекция, пока данные не будут
  загружены или восстановлены;
- при ошибке обновления уже показанные шутки остаются на экране.

Запись выполняется через временный файл и переименование. При замене создаётся
резервный `.previous`-файл, поэтому сбой записи не должен автоматически
уничтожить прежнюю коллекцию.

## 12. Резервная копия и хранение данных

Копия хранится только во внутреннем хранилище:

```text
filesDir/backup/jokes_backup.json
```

Её структура:

```json
{
  "version": 2,
  "createdAt": "2026-10-25T14:00:00+03:00",
  "jokes": []
}
```

`JsonBackupRepository` проверяет непустую коллекцию, пишет временный файл,
проверяет его чтением и уникальность `id`, затем атомарно заменяет основную
копию. Восстановление не требует сети. Отдельно поддерживаются удаление копии и
получение её даты и количества шуток для UI.

| Данные | Место хранения |
|---|---|
| Логин, имя, возраст, аватар | `SharedPreferences` `punchline_user` |
| Соль и хеш пароля | `SharedPreferences` `punchline_user` |
| Тема, масштаб шрифта, язык | `SharedPreferences` `punchline_settings` |
| Флаг инициализации кэша | `SharedPreferences` `joke_cache_state` |
| Кэш шуток | `filesDir/jokes_cache.json` |
| Резервная копия | `filesDir/backup/jokes_backup.json` |

В манифесте указано `android:allowBackup="false"`, поэтому данные приложения не
передаются в системный Android backup.

## 13. Настройки и интерфейс

`SettingsActivity` позволяет изменить имя, возраст, аватар, системную, светлую
или тёмную тему, масштаб текста от 85% до 130%, язык интерфейса, а также создать,
восстановить или удалить копию и очистить кэш.

Имя и возраст проверяются тем же валидатором, что и при регистрации. Тема,
шрифт и язык сохраняются сразу, профиль — по кнопке «Сохранить профиль».

### Тема и шрифт

`PunchlineTheme` выбирает `lightColorScheme` или `darkColorScheme` по
`ThemeMode` и системному режиму. Размер текста вычисляется из выбранного
масштаба. Настройки наблюдаются через `StateFlow` на всех четырёх Activity.

### Язык

Есть ресурсы `values/strings.xml` (`ru`) и `values-en/strings.xml` (`en`).
`PunchlineTheme` предоставляет Compose локализованный `Context` и `Resources`.
Ошибки валидации и одноразовые сообщения передаются как типизированные enum-ключи
и переводятся в UI. Тексты JokeAPI остаются английскими и намеренно не
переводятся.

`LoggedActivity` переопределяет `onCreate`, `onStart`, `onRestart`, `onResume`,
`onPause`, `onStop` и `onDestroy`. Сначала вызывается `super`, затем пишется
строка с тегом `Lab1Lifecycle` в формате `ИмяActivity: имяМетода`.

```bash

```

показать заранее сохранённый вывод, а живой запуск использовать как дополнение.

## 15. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Неверное поле | Текст ошибки рядом с полем |
| Неверная пара логина и пароля | Сообщение без раскрытия причины |
| Нет сети при первом запуске | Состояние ошибки и кнопка повтора |
| Нет сети, есть кэш | Ранее загруженные шутки доступны |
| API вернул меньше 12 шуток | Ошибка, старый кэш сохраняется |
| Некорректный JSON | Обрабатывается как ошибка данных |
| Нет резервной копии | Восстановление и удаление отключены |
| Ошибка записи копии | Старый файл по возможности сохраняется |
| Ошибка восстановления | Пользователь получает понятное сообщение |

Технические исключения не выводятся пользователю напрямую. ViewModel показывает
типизированные сообщения из ресурсов.

## 16. Безопасность и границы решения

Реализовано:

- пароль не хранится открытым;
- для каждого пароля создаётся уникальная соль;
- используется итеративный HMAC-SHA256;
- хеши сравниваются за постоянное время;
- пароль, соль и хеш не передаются через `Intent` и не пишутся в Logcat;
- используется внутреннее хранилище и `MODE_PRIVATE`;
- системный backup отключён;
- экспортирована только launcher-Activity;
- JokeAPI вызывается по HTTPS;
- версия и структура JSON проверяются перед использованием.

Границы решения:

- авторизация только локальная, без сервера и синхронизации;
- файлы защищены песочницей приложения, но дополнительно не шифруются;
- собственный хешировщик подходит для учебной демонстрации, но не заменяет
  проверенную криптографическую библиотеку;
- JokeAPI может быть недоступен или изменить формат ответа;
- unit- и UI-тесты в минимальной конфигурации отсутствуют;
- два обязательных стека Logcat нужно получить вручную.

Если спросят, почему решение безопасно:

> «Оно безопаснее открытого хранения пароля: используются уникальная соль,
> итеративный HMAC, постоянное сравнение и отсутствие секретов в Intent и
> логах. Для production я бы применил проверенную криптографическую библиотеку,
> Android Keystore и серверную аутентификацию».

## 18. Ответы на вероятные вопросы

### Почему четыре Activity, а не одна с Navigation Compose?

Отдельная Activity для каждого экрана — требование лабораторной. Внутри каждой
используется Compose, поэтому обязательная Activity-навигация сочетается с
современным декларативным интерфейсом.

### Почему ViewModel не содержит Activity или Context?

ViewModel должна переживать реконфигурацию и не удерживать Activity в памяти.
Контекст нужен только реализациям хранилищ, которым передаётся
`applicationContext`; ViewModel получает готовые интерфейсы репозиториев.

### Почему используется `StateFlow`?

Он хранит последнее состояние независимо от подписчика и позволяет Compose
обновлять экран при изменении данных. Activity собирает состояние через
`collectAsStateWithLifecycle()` и не превращает его во второй источник истины.

### Почему сообщения передаются через `Channel`?

Snackbar и навигационные следствия являются одноразовыми событиями. В
постоянном состоянии они могли бы повториться после рекомпозиции или поворота.
`Channel` передаёт событие подписчику один раз.

### Почему API-клиент не находится в Activity?

Activity отвечает за жизненный цикл и переходы. Сеть и JSON находятся в
data-слое, поэтому их можно тестировать без Activity, заменить реализацию и не
смешивать сетевые ошибки с UI.

### Почему API возвращает не ровно 12 шуток?

Запрос возвращает до 10 элементов. Репозиторий повторяет запросы, пока не
соберёт минимум 12 уникальных шуток, и ограничивает итог 20 элементами. Это
соответствует диапазону карточек из задания.

### Как работают дедупликация и ограничение?

`JokeFeedPolicy.merge()` объединяет пакеты, применяет `distinctBy { it.id }` и
`take(20)`. Повторяющиеся шутки не попадают в ленту, а коллекция не растёт
бесконечно.

### Почему кэш хранится в JSON-файле, а не в Room?

Коллекция небольшая, хранится одним массивом и редко заменяется полностью.
JSON-файл проще показать на первой лабораторной. Для большого каталога, поиска
и связей лучше подошёл бы Room.

### Что произойдёт без интернета?

Если кэш или копия уже существует, приложение читает данные локально. Если
данных нет, показывается состояние ошибки с понятным текстом и кнопкой повтора.

### Чем кэш отличается от резервной копии?

Кэш обновляется сетевой загрузкой и используется для обычного показа. Копия
создаётся пользователем, не удаляется при очистке кэша и нужна для явного
восстановления после потери текущей коллекции.

### Как копия защищена от повреждения?

Новая копия сначала пишется во временный файл и проверяется чтением. Только
после проверки выполняется замена. Старая копия используется как резерв на время
операции.

### Что происходит при повороте экрана?

Состояние экранов находится в ViewModel и `StateFlow`, поэтому переживает
пересоздание Activity. Масштаб, тема, язык, профиль и кэш сохранены постоянно.
Пароль в `SavedStateHandle` намеренно не сохраняется.

### Где обрабатывается ошибка сети?

Исключение возникает в `RemoteJokeRepository`, превращается в результат
сценария ViewModel, затем в типизированное сообщение для UI. Compose не получает
HTTP-детали.

### Почему пароль передаётся как `CharArray`?

Массив символов можно явно затереть после хеширования, в отличие от неизменяемой
строки. Это снижает время нахождения секрета в памяти, хотя поле Compose всё
равно содержит строковое состояние UI. Это дополнительная мера, а не абсолютная
гарантия.

### Какие методы жизненного цикла показаны?

Показан полный набор базовых методов Activity. Дополнительно
`collectAsStateWithLifecycle()` подписывает Compose на состояние только в
активном состоянии экрана.

### Почему только `StartActivity` экспортирована?

Её запускает системный launcher. Остальные экраны нужны только внутри
приложения, поэтому `exported="false"` уменьшает доступную поверхность.

### Как реализована локализация?

Строки находятся в русских и английских ресурсах. Язык хранится в
`SharedPreferences`, наблюдается через `StateFlow` и передаётся в
`PunchlineTheme`, который предоставляет локализованный Compose-контекст.

### Какие ограничения проекта?

Локальная авторизация без сервера, отсутствие синхронизации между устройствами и
дополнительного шифрования файлов, отсутствие автоматических тестов и готовых
логов. Эти ограничения объясняются рамками лабораторной.
