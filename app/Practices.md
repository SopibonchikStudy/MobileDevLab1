# Практики и отличительные черты проекта Bookline

Документ описывает практики, которые фактически использованы в исходном коде
приложения Bookline, а не только заявлены в проектной документации. Основной
акцент сделан на Android-разработке, UI, архитектуре, работе с состоянием,
навигации, хранении данных, безопасности, тестировании и сборке.

## 1. Краткая характеристика проекта

Bookline — учебное Android-приложение для локального каталога книг. Приложение
позволяет зарегистрироваться, войти, просмотреть список из 12 книг, изменить
профиль и оформление, а также создать, восстановить или удалить резервную копию
каталога.

| Параметр | Использованное решение |
|---|---|
| Язык | Kotlin |
| UI | Jetpack Compose |
| Дизайн-система | Material Design 3 |
| Минимальная версия | Android 7.0, API 24 |
| Экраны | 4 отдельные Activity |
| Архитектурный подход | Прагматичный MVVM с разделением на слои |
| Управление состоянием | `StateFlow`, неизменяемые UI-модели, одноразовые события через `Channel` |
| Асинхронность | Kotlin Coroutines, `Dispatchers.IO`, `viewModelScope` |
| Локальные данные | `SharedPreferences` и JSON-файлы во внутреннем хранилище |
| Навигация | `Intent`, `registerForActivityResult`, типизированные `ActivityResultContract` |
| Журналирование | Общий `LoggedActivity` и тег `Lab1Lifecycle` |
| Тестирование | JUnit-тесты домена и демонстрационного каталога |
| Сборка | Gradle Kotlin DSL и version catalog |

Приложение работает офлайн: для основного каталога не требуется сеть или
серверная авторизация. В манифесте нет разрешения `INTERNET`.

## 2. Основные практики

### 2.1. Нативная Android-разработка на Kotlin

Проект целиком реализован на Kotlin. Используются data-классы, sealed-типы,
расширения Kotlin, именованные аргументы, `runCatching`, `Result`, корутины и
`Flow`. Основной UI написан декларативно на Jetpack Compose; XML используется
только для ресурсов, темы и манифеста.

Практика прослеживается в:

- `src/main/java/com/example/a1lab/`;
- `src/main/java/com/example/a1lab/domain/`;
- `src/main/java/com/example/a1lab/viewmodel/`.

Отличительная черта: четыре самостоятельные Activity сохранены как обязательная
часть учебного задания, а не заменены одной Activity с Compose Navigation.

### 2.2. Jetpack Compose и Material Design 3

Экраны построены из composable-функций и компонентов Material 3: `Scaffold`,
`TopAppBar`, `Card`, `OutlinedTextField`, `Button`, `OutlinedButton`,
`AssistChip`, `FilterChip`, `Slider`, `AlertDialog`, `SnackbarHost`,
`CircularProgressIndicator` и других.

Применены следующие практики:

- единая тема `BooklineTheme` для всего приложения;
- светлая, тёмная и системная цветовые схемы;
- собственные семантические цвета (`Emerald`, `Amber`, `Terracotta`, `Ink`);
- типографика Material 3 с поддержкой пользовательского масштаба шрифта;
- повторно используемые компоненты `BrandHeader`, `BrandedBackground`,
  `BooklineTextField`, `InitialsBadge`, `SectionTitle` и `BooklineLogo`;
- `LazyColumn` для эффективного отображения прокручиваемого каталога;
- стабильные `key = { it.id }` для элементов списка;
- `verticalScroll` на формах, которые могут не поместиться на небольшом экране;
- `Scaffold` с корректной передачей `PaddingValues` в содержимое;
- `enableEdgeToEdge()` на всех Activity;
- локальная отрисовка логотипа, фона и обложек средствами Compose `Canvas`, без
  необходимости загружать изображения из сети.

### 2.3. State hoisting и разделение экранов на stateful и stateless части

Корневые composable получают `UiState` и колбэки, а вложенные элементы не
обращаются к ViewModel и репозиториям напрямую. Activity подписывается на
состояние ViewModel, применяет тему и передаёт данные в экран.

В результате:

- экран знает только о данных и пользовательских действиях;
- ViewModel не зависит от Compose;
- UI можно отобразить с произвольным тестовым состоянием;
- состояние формы не размазано по множеству локальных mutable-переменных;
- изменение состояния вызывает предсказуемую рекомпозицию.

Примеры: `StartScreen`, `RegistrationScreen`, `ContentScreen` и
`SettingsScreen` принимают соответствующие `UiState` и функции-колбэки.

### 2.4. MVVM и однонаправленный поток данных

Каждой Activity соответствует отдельная ViewModel:

| Activity | ViewModel | Состояние |
|---|---|---|
| `StartActivity` | `StartViewModel` | `StartUiState` |
| `RegistrationActivity` | `RegistrationViewModel` | `RegistrationUiState` |
| `ContentActivity` | `ContentViewModel` | `ContentUiState` |
| `SettingsActivity` | `SettingsViewModel` | `SettingsUiState` |

Поток данных организован по принципу unidirectional data flow:

```text
UI event -> ViewModel -> repository/storage
         <- StateFlow <- новое состояние
```

Практики реализации:

- UI-состояния представлены неизменяемыми `data class`;
- снаружи доступен только read-only `StateFlow`;
- изменение выполняется через приватный `MutableStateFlow`;
- состояние собирается через `collectAsStateWithLifecycle()`, поэтому подписка
  учитывает жизненный цикл Activity;
- ViewModel не хранит ссылки на `Activity`, `Context`, `View` или composable;
- фоновые операции запускаются в `viewModelScope` и автоматически отменяются при
  очистке ViewModel;
- Activity обрабатывает только навигационные следствия и системные результаты.

### 2.5. Одноразовые события отделены от постоянного состояния

Сообщения и навигационные события не помещены в `UiState`, где они могли бы
повторно сработать после рекомпозиции. Для них используются буферизованные
`Channel` и `receiveAsFlow()`:

- `StartEvent.Authenticated` и `StartEvent.Message`;
- `SettingsEvent.Message` и `SettingsEvent.ProfileUpdated`;
- строковые события загрузки и операций с копией в `ContentViewModel`;
- логин после успешной регистрации в `RegistrationViewModel`.

Activity собирает события через `LaunchedEffect`. Это отделяет долговременное
состояние экрана от действий, которые должны произойти один раз.

### 2.6. Прагматичная многослойная архитектура

Код разделён по ответственности:

| Пакет | Назначение |
|---|---|
| `ui` | Compose-экраны, компоненты и тема |
| `domain` | Модели книги, пользователя, настроек и чистые правила валидации |
| `data` | Контракты репозиториев, JSON-кодек, каталог, копия и контейнер зависимостей |
| `storage` | Реализации пользовательских настроек, профиля и хеширования пароля |
| `viewmodel` | Состояние и сценарии конкретного экрана |
| `navigation` | Типизированные контракты межэкранных результатов |
| `logging` | Общая реализация журналирования жизненного цикла |

Домен не импортирует Android UI, Compose, JSON или сетевые типы. JSON-типы также
не попадают в UI: преобразование выполняется в `BookJsonCodec` и репозиториях.

### 2.7. Программирование через интерфейсы и внедрение зависимостей

Определены интерфейсы `BookRepository`, `BackupRepository`, `UserRepository` и
`SettingsRepository`. Конкретные реализации находятся в `data` и `storage`.

Зависимости передаются через конструктор. Общий граф объектов создаётся в
`AppContainer`, который инициализируется в `BooklineApplication`. ViewModel
создаются через `viewModelFactory` и получают готовые абстракции.

Практические эффекты:

- Compose-экраны не знают, откуда приходят данные;
- `JsonBookRepository` можно заменить реализацией REST API без изменения UI;
- реализации репозиториев можно подменить в тестах;
- отсутствует скрытое создание хранилищ внутри ViewModel;
- зависимости явно видны в конструкторах.

Это ручной dependency injection. В проекте нет Hilt, Koin или другого
DI-фреймворка, что для данного размера приложения уменьшает сложность.

### 2.8. Асинхронная работа с хранилищем

Файловые операции и работа с `SharedPreferences` для профиля выполняются через
`suspend`-функции и `withContext(Dispatchers.IO)`. Операции запускаются из
`viewModelScope`, а не из главного потока.

Используются:

- `suspend fun` для репозиториев;
- `withContext(Dispatchers.IO)` для дискового ввода-вывода;
- `StateFlow` для настроек, которые применяются сразу;
- флаг загрузки для блокировки повторных операций;
- `runCatching` и `Result` для преобразования исключений в пользовательские
  сообщения.

### 2.9. Явная обработка состояний интерфейса

В интерфейсе предусмотрены отдельные состояния:

- начальная загрузка каталога;
- успешный список книг;
- пустой каталог;
- ошибка загрузки;
- недоступность резервной копии;
- выполнение операции с копией;
- ошибки отдельных полей;
- общая ошибка формы;
- подтверждение необратимых или заменяющих действий.

Для обратной связи применяются `supportingText` у полей, `Snackbar`,
`CircularProgressIndicator` и `AlertDialog`. Ошибка не ограничивается записью в
Logcat или изменением цвета.

### 2.10. Валидация как чистая доменная логика

`Validation` не зависит от Android и возвращает типизированный
`ValidationResult`: `Valid` или `Invalid(message)`.

Проверяются:

- имя — 2–40 символов после `trim()`;
- логин — 3–64 символа;
- формат e-mail, если логин содержит `@`;
- пароль — 6–64 символа;
- совпадение пароля и подтверждения;
- необязательный возраст — целое число от 6 до 120.

Практики:

- одна функция проверяет одно правило;
- ошибки показываются рядом с соответствующим полем;
- общая ошибка формы отделена от ошибок полей;
- при неудачном входе логин не стирается;
- проверка выполняется до сохранения аккаунта;
- настройки профиля используют те же доменные правила, что и регистрация.

### 2.11. Типизированная навигация через Activity Result

Межэкранные результаты описаны через `ActivityResultContract`:

- `RegistrationContract` возвращает логин после регистрации;
- `SettingsContract` возвращает логин и признак изменения профиля.

Это позволяет:

- не использовать глобальные переменные;
- не передавать пароль, хеш или полный профиль через `Intent`;
- явно описать входные и выходные данные маршрута;
- автоматически разобрать `RESULT_OK` и отсутствие результата;
- тестировать контракт как обычный Kotlin-объект.

### 2.12. Управление стеком Activity

Навигация соответствует заданной схеме:

```text
StartActivity -> RegistrationActivity -> StartActivity
StartActivity -> ContentActivity -> SettingsActivity -> ContentActivity
```

Использованы практики:

- после успешного входа `StartActivity` вызывает `finish()`;
- после регистрации `RegistrationActivity` возвращает результат и закрывается;
- `SettingsActivity` возвращает результат в `ContentActivity`;
- `ContentActivity` входит в настройки через `registerForActivityResult`;
- системная кнопка «Назад» в настройках возвращает к каталогу;
- на экране каталога выход подтверждается `AlertDialog`;
- повторные нажатия на навигационные кнопки ограничены флагами `settingsOpen` и
  `navigating`;
- сохранён только необходимый элемент состояния `profileChanged` через
  `onSaveInstanceState`.

### 2.13. Централизованное журналирование жизненного цикла

Все четыре Activity наследуют `LoggedActivity : ComponentActivity()`.
Базовый класс переопределяет `onCreate`, `onStart`, `onRestart`, `onResume`,
`onPause`, `onStop` и `onDestroy`.

В каждом методе:

1. вызывается `super`;
2. записывается событие с тегом `Lab1Lifecycle`;
3. имя Activity берётся через `this::class.simpleName`.

Формат записи:

```text
StartActivity: onCreate
StartActivity: onStart
StartActivity: onResume
```

Отличительная черта: наследники не дублируют lifecycle-код, а имя класса
автоматически соответствует конкретной Activity. В логи не попадают логин,
пароль, хеш или содержимое профиля.

### 2.14. Локальное хранение с явными границами

Данные разделены по назначению:

| Данные | Где хранятся |
|---|---|
| Профиль, соль и хеш | `SharedPreferences` `bookline_user` |
| Тема и масштаб шрифта | `SharedPreferences` `bookline_settings` |
| Флаг инициализации каталога | `SharedPreferences` `catalog_state` |
| Кэш каталога | `filesDir/catalog_cache.json` |
| Резервная копия | `filesDir/backup/content_backup.json` |

Использование `SharedPreferences` для небольшого профиля и настроек разрешено
условиями проекта. Во внешнее хранилище приложение не пишет и не требует
разрешений на доступ к файлам.

### 2.15. JSON-кодек и версионирование формата

Сериализация каталога вынесена в отдельный `BookJsonCodec`. В JSON сохраняются
все поля `BookCard`, включая статус доступности и `coverUrl`.

Резервная копия содержит:

```json
{
  "version": 1,
  "createdAt": "2026-10-24T12:00:00+03:00",
  "books": []
}
```

Перед использованием проверяются версия формата, непустой список и уникальность
идентификаторов книг. Домен не зависит от конкретной JSON-библиотеки, для
кодирования используется встроенный `org.json`.

### 2.16. Атомарная запись файлов и защита от повреждения

Каталог и резервная копия сначала записываются во временный файл. Затем целевой
файл заменяется, а предыдущая версия временно сохраняется как `.previous`.

Если замена не удалась, выполняется попытка восстановить предыдущий файл и
вернуть ошибку. Копия предварительно читается и валидируется до замены основной.

Практический результат:

- повреждённая или незавершённая запись не должна заменить рабочие данные;
- ошибка чтения не приводит к молчаливой перезаписи копии;
- успешное сообщение показывается только после фактической записи;
- исходный каталог остаётся доступным при неудачной операции.

### 2.17. Безопасная работа с паролем

Для учебной локальной аутентификации реализован отдельный `PasswordHasher`:

- генерируется случайная 16-байтовая соль через `SecureRandom`;
- используется собственное итерированное вычисление на `HmacSHA256`;
- выполняется 20 000 итераций;
- сравнение хешей производится в постоянном времени;
- пароль передаётся как `CharArray`, а временный байтовый массив обнуляется после
  использования;
- в `SharedPreferences` хранятся только соль и хеш;
- пароль и хеш не передаются через `Intent`;
- секреты не выводятся в Logcat;
- системное резервное копирование приложения отключено через
  `android:allowBackup="false"`.

Это существенно лучше хранения пароля в открытом виде. При этом реализация не
является полноценной заменой PBKDF2, Argon2 или серверной аутентификации:
параметры KDF и профиль безопасности следует пересмотреть перед реальным
использованием.

### 2.18. Локализация и доступность

Пользовательские строки преимущественно вынесены в `strings.xml` и читаются
через `stringResource`. Для чисел используются строковые шаблоны, для рейтинга и
дат — `Locale`.

Элементы доступности:

- у обложки книги есть `contentDescription` с названием книги;
- у логотипа есть текстовое описание;
- у кнопки настроек задана область 64 × 48 dp и описание действия;
- ошибки полей имеют текстовое представление, а не только цвет;
- статус доступности книги одновременно кодируется цветом и текстом;
- поддерживается RTL через `android:supportsRtl="true"`;
- для полей задан подходящий тип клавиатуры, а пароль визуально скрывается;
- основные кнопки имеют высоту 52 dp, что превышает рекомендуемый минимум 48 dp.

### 2.19. Тестирование домена и демонстрационных данных

Добавлены JUnit-тесты, которые не требуют Android-эмулятора:

- границы длины имени, логина и пароля;
- корректный и некорректный e-mail;
- совпадение и несовпадение паролей;
- допустимые и недопустимые значения возраста;
- количество книг — ровно 12;
- уникальность идентификаторов;
- непустые название, автор и жанр;
- рейтинг в диапазоне 0.0–5.0;
- год не превышает текущий;
- наличие всех трёх статусов доступности.

Есть также стандартная инструментальная проверка имени пакета. Тестовые
зависимости Compose UI Test и Espresso присутствуют, но содержательных
Compose-тестов и тестов Activity в проекте пока нет.

### 2.20. Конфигурация сборки и версионирование зависимостей

Проект использует:

- Gradle Kotlin DSL;
- version catalog `gradle/libs.versions.toml`;
- Compose BOM для согласования версий Compose-библиотек;
- `minSdk = 24`, `targetSdk = 37`;
- включённый configuration cache;
- R8-оптимизацию release-сборки;
- отдельный файл правил `keepRules`;
- отключение системного backup для защиты локальных секретов;
- отсутствие сетевых зависимостей и разрешения `INTERNET`.

### 2.21. Защита от повторных действий

В ViewModel и Activity используются простые, но важные проверки:

- `navigating` не позволяет повторно открыть каталог после входа;
- `settingsOpen` не позволяет создать несколько экземпляров настроек;
- `isSubmitting` блокирует повторную отправку формы;
- `isLoading` блокирует повторные операции с каталогом и копией;
- повторное нажатие кнопки «Назад» на экране данных сначала показывает диалог,
  а затем завершает приложение.

## 3. Отличительные черты проекта

### 3.1. Локальный офлайн-каталог с готовностью к сетевому источнику

Текущий источник данных локальный, но UI зависит от `BookRepository`, а не от
JSON-файла. Для подключения сервера потребуется реализовать тот же интерфейс и
выполнить маппинг DTO в `BookCard`; экран каталога при этом менять не требуется.

### 3.2. Четыре Activity и при этом современное управление состоянием

Проект сохраняет обязательную учебную модель четырёх экранов на Activity, но не
перегружает Activity бизнес-логикой. Навигация остаётся Activity-based, а
состояние и сценарии находятся в ViewModel.

### 3.3. Собственный визуальный язык Bookline

Вместо стандартного шаблона использованы:

- изумрудная, янтарная и терракотовая палитра;
- тёплый светлый и глубокий тёмный фоны;
- градиентный декоративный фон с линиями книжных полок;
- логотип раскрытой книги, нарисованный локально;
- крупные скругления карточек;
- локальные обложки с инициалами автора;
- отдельное приветствие для первого и повторного входа.

### 3.4. Практичный сценарий резервного копирования

Пользователь может не только создать копию, но и проверить полный цикл:

```text
создать копию -> очистить каталог -> восстановить копию -> удалить копию
```

Пустой каталог не оставляет пользователя на тупиковом экране: он предлагает
восстановить копию или открыть настройки. Кнопки восстановления и удаления
зависят от фактического наличия копии.

### 3.5. Секреты не участвуют в навигационном контракте

Между Activity передаются только логин и флаг изменения профиля. Пароль
проверяется внутри репозитория и не попадает в `Intent`, UI-состояние после
завершения операции или журнал.

### 3.6. Единая инфраструктура жизненного цикла

Журналирование всех Activity находится в одном базовом классе. Это уменьшает
дублирование и снижает риск пропустить событие в одной из Activity.

### 3.7. Аккуратная обработка локальных файлов

Для учебного проекта реализация выходит за рамки простого `writeText`: есть
временный файл, проверка содержимого, замена через промежуточный файл и
восстановление предыдущей версии при сбое.

## 5. Практики, которых в проекте нет

Этот раздел важен, чтобы не приписывать проекту неиспользованные подходы.

В текущей реализации отсутствуют:

- Compose Navigation как основа маршрутизации;
- `MainActivity` как единственная Activity;
- сетевой слой, Retrofit, OkHttp, API, кэширование HTTP-ответов и пагинация;
- серверная авторизация и OAuth/JWT;
- Room или SQL-база данных;
- DataStore;
- Hilt, Koin или другой DI-фреймворк;
- шифрование всего локального хранилища через Android Keystore;
- BiometricPrompt;
- полноценная тема через динамическую палитру Android 12+ как единственный
  механизм выбора темы;
- real-time синхронизация между устройствами;
- поиск, фильтрация, сортировка и избранное;
- содержательные Compose UI-тесты;
- интеграционные тесты репозиториев и ViewModel;
- CI-конфигурация;
- полноценная локализация на несколько языков;
- единая ресурсная система для всех сообщений об ошибках, часть которых пока
  задана строками в ViewModel;
- сохранение формы через `SavedStateHandle` на случай полного завершения
  процесса.

## 6. Ограничения и зоны для улучшения

Ниже перечислены ограничения, выявленные по коду и не мешающие демонстрации
учебного сценария.

1. **Парольный KDF.** Итерированный HMAC-SHA256 защищает лучше простого хеша,
   но для production-системы предпочтительны стандартизированные PBKDF2,
   scrypt или Argon2 с проверенным числом итераций.
2. **Локальная модель аккаунта.** На устройстве хранится только один аккаунт;
   многопользовательская регистрация и восстановление через сервер не
   реализованы.
3. **Ошибки чтения каталога.** `JsonBookRepository.getBooks()` при повреждённом
   кэше возвращает пустой список. Для пользователя это выглядит как пустой
   каталог, а не отдельная ошибка чтения.
4. **Информация о повреждённой копии.** `getBackupInfo()` может вернуть `null`
   при повреждённом файле, после чего UI считает, что копии нет. Это безопасно с
   точки зрения отсутствия перезаписи, но недостаточно информативно.
5. **Сохранение форм.** ViewModel переживает поворот экрана, однако состояние
   полей не сохраняется через `SavedStateHandle` после смерти процесса.
6. **Тестовая пирамида.** Хорошо покрыты чистые правила и демо-данные, но нет
   тестов JSON-репозиториев, хешера, ViewModel, навигации и Compose-экранов.
7. **Доступность.** Не у всех пиктограмм и кнопок «Назад» есть семантические
   описания; символьные иконки (`⚙`, `↻`, `‹`) могут по-разному читаться
   экранным диктором. Нужны автоматизированные accessibility-проверки.
8. **Жизненный цикл.** Нет отдельного теста или автоматической проверки
   обязательных записей `Lab1Lifecycle`; сценарии Logcat проверяются вручную.
9. **Резервное копирование.** JSON-копия защищена только приватным каталогом
   приложения; отдельного шифрования файла или контроля целостности нет.
10. **Архитектурная граница.** Часть пользовательских текстов формируется в
    ViewModel, что усложняет полную локализацию и переиспользование сообщений.

## 7. Как кратко описать проект на защите

«Bookline — офлайн-приложение библиотеки на Kotlin и Jetpack Compose с четырьмя
Activity. UI построен на Material 3 и отделён от логики через MVVM: Activity
отвечает за навигацию и жизненный цикл, ViewModel хранит неизменяемое состояние
в `StateFlow` и обрабатывает действия, репозитории отвечают за данные, а domain
содержит чистую валидацию и модели. Зависимости передаются через собственный
`AppContainer`, поэтому локальный JSON-источник можно заменить сетевым без
переработки экранов.

Для регистрации используется уникальная соль и итерированный HMAC-хеш;
пароль не передаётся между Activity и не пишется в логи. Каталог и резервная
копия хранятся в приватном JSON-хранилище и записываются атомарно. Навигация
типизирована через `ActivityResultContract`, а все четыре Activity журналируют
жизненный цикл через общий `LoggedActivity` с тегом `Lab1Lifecycle`.
Предусмотрены состояния загрузки, пустого списка, ошибок, подтверждающие
диалоги, светлая/тёмная тема и масштаб текста. Модульные JUnit-тесты проверяют
границы валидации и целостность демонстрационного каталога».
