# Практики и отличительные черты проекта Punchline

Документ описывает практики, фактически использованные в приложении
**Punchline**, а не только заявленные в проектной документации. Основной акцент
сделан на Android, Jetpack Compose, архитектуре, работе с сетевым API,
состоянием, локальным хранением, безопасностью и тестированием.

## 1. Краткая характеристика проекта

Punchline — учебное Android-приложение для загрузки и просмотра шуток JokeAPI.
Пользователь регистрируется, входит, получает коллекцию из 12–20 уникальных
шуток, меняет профиль и оформление, а также создаёт, восстанавливает и удаляет
локальную резервную копию коллекции.

| Параметр | Решение |
|---|---|
| Язык | Kotlin |
| UI | Jetpack Compose |
| Дизайн-система | Material Design 3 |
| Минимальная версия | Android 7.0, API 24 |
| Экраны | четыре отдельные Activity |
| Архитектура | прагматичный MVVM и слои приложения |
| Состояние | `StateFlow`, неизменяемые UI-модели, одноразовые события через `Channel` |
| Асинхронность | Kotlin Coroutines, `Dispatchers.IO`, `viewModelScope` |
| Данные JokeAPI | `HttpURLConnection` и `org.json` |
| Локальные данные | `SharedPreferences` и JSON-файлы во внутреннем хранилище |
| Навигация | `Intent`, `ActivityResultContract` |
| Логирование | общий `LoggedActivity`, тег `Lab1Lifecycle` |
| Тестирование | JUnit для domain/data и JSON-кодека JokeAPI |
| Сборка | Gradle Kotlin DSL и version catalog |

Первый показ коллекции и явное обновление требуют интернет. После успешной
загрузки шутки сохраняются в кэше и резервной копии и открываются без сети. В манифесте
объявлено разрешение `INTERNET`.

## 2. Основные практики

### 2.1. Нативная Android-разработка на Kotlin

Проект реализован на Kotlin и использует data-классы, enum-типы, расширения,
именованные аргументы, `runCatching`, `Result`, корутины и `Flow`. Основной UI
написан декларативно на Jetpack Compose; XML применяется для ресурсов, темы и
манифеста.

Отличительная черта: четыре самостоятельные Activity сохранены как обязательная
часть задания, а не заменены одной Activity с Compose Navigation.

### 2.2. Jetpack Compose и Material Design 3

Экраны построены из composable-функций и компонентов Material 3: `Scaffold`,
`TopAppBar`, `Card`, `OutlinedTextField`, `Button`, `OutlinedButton`,
`AssistChip`, `FilterChip`, `Slider`, `AlertDialog`, `SnackbarHost` и
`CircularProgressIndicator`.

Практики:

- единая тема `PunchlineTheme` для всего приложения;
- светлая, тёмная и системная цветовые схемы;
- собственные семантические цвета `Emerald`, `Amber`, `Terracotta`, `Ink`;
- типографика Material 3 с пользовательским масштабом шрифта;
- повторно используемые `BrandHeader`, `BrandedBackground`,
  `PunchlineTextField`, `InitialsBadge`, `SectionTitle` и `PunchlineLogo`;
- `LazyColumn` для прокручиваемой ленты шуток;
- стабильные ключи `key = { it.id }` из API;
- `verticalScroll` на формах, которые могут не поместиться на небольшом экране;
- передача `PaddingValues` из `Scaffold` в содержимое;
- `enableEdgeToEdge()` на всех Activity;
- локальная отрисовка логотипа и фона средствами Compose.

Логотип в виде улыбающегося смайла и графические бейджи категорий не требуют
загрузки изображений. Сетевой контент остаётся текстовым и доступен при любом
размере экрана.

### 2.3. State hoisting

Корневые composable получают `UiState` и колбэки, а вложенные элементы не
обращаются к ViewModel и репозиториям напрямую. Activity подписывается на
состояние ViewModel, применяет тему и передаёт данные в stateless-экран.

Это даёт:

- экран, который знает только о данных и действиях пользователя;
- отсутствие зависимости ViewModel от Compose;
- возможность показать произвольное тестовое состояние;
- предсказуемую рекомпозицию.

Примеры: `StartScreen`, `RegistrationScreen`, `ContentScreen` и
`SettingsScreen`.

### 2.4. MVVM и однонаправленный поток данных

| Activity | ViewModel | Состояние |
|---|---|---|
| `StartActivity` | `StartViewModel` | `StartUiState` |
| `RegistrationActivity` | `RegistrationViewModel` | `RegistrationUiState` |
| `ContentActivity` | `ContentViewModel` | `ContentUiState` |
| `SettingsActivity` | `SettingsViewModel` | `SettingsUiState` |

Поток данных:

```text
UI event -> ViewModel -> repository/storage
         <- StateFlow <- новое состояние
```

Практики:

- состояния — неизменяемые `data class`;
- снаружи доступен только read-only `StateFlow`;
- изменения идут через приватный `MutableStateFlow`;
- подписка выполняется через `collectAsStateWithLifecycle()`;
- ViewModel не хранит `Activity`, `Context`, `View` или composable;
- фоновые операции запускаются в `viewModelScope`;
- навигационные следствия обрабатывает Activity.

### 2.5. Одноразовые события

Сообщения не помещены в постоянное состояние, где они могли бы повториться после
рекомпозиции. Для них используются буферизованные `Channel` и `receiveAsFlow()`:

- `StartEvent.Authenticated` и `StartEvent.Message`;
- `SettingsEvent.Message` и `SettingsEvent.ProfileUpdated`;
- сообщения загрузки, обновления и восстановления в `ContentViewModel`.

Activity собирает события через `LaunchedEffect` и выполняет переход или
показывает `Snackbar` однократно.

### 2.6. Многослойная архитектура

| Пакет | Назначение |
|---|---|
| `ui` | Compose-экраны, компоненты и тема |
| `domain` | модели шутки, пользователя, настроек и валидация |
| `data` | контракты, JokeAPI, JSON-кодек, кэш, копия и DI-контейнер |
| `storage` | пользователь, настройки и хеширование пароля |
| `viewmodel` | состояние и сценарии экрана |
| `navigation` | типизированные контракты Activity Result |
| `logging` | журналирование жизненного цикла |

Domain не импортирует Android UI, Compose, JSON или сетевые типы. JSON-типы и
ответ JokeAPI преобразует `JokeJsonCodec` в data-слое.

### 2.7. Программирование через интерфейсы

Определены интерфейсы `JokeRepository`, `BackupRepository`, `UserRepository` и
`SettingsRepository`. Реализации размещены в `data` и `storage`, зависимости
передаются через конструктор. Общий граф создаётся в `AppContainer`, который
инициализируется в `PunchlineApplication`.

Практические эффекты:

- Compose не знает, откуда приходят шутки;
- `RemoteJokeRepository` можно заменить фейком в тестах;
- отсутствует скрытое создание HTTP-клиента внутри ViewModel;
- зависимости явно видны в конструкторах.

Используется ручной dependency injection, без Hilt и Koin.

### 2.8. Асинхронная работа с сетью и хранилищем

Сетевые и файловые операции выполняются через `suspend`-функции и
`withContext(Dispatchers.IO)`. Вызовы запускаются из `viewModelScope`, поэтому
главный поток остаётся отзывчивым, а работа отменяется при очистке ViewModel.

Используются:

- таймауты `connectTimeout` и `readTimeout`;
- проверка HTTP-статуса до чтения тела;
- буферизованное чтение ответа в UTF-8;
- `disconnect()` в `finally`;
- флаг загрузки для блокировки повторных операций;
- `runCatching` и `Result` для преобразования исключений в сообщения UI.

### 2.9. Явные состояния интерфейса

Для ленты шуток предусмотрены:

- первая загрузка;
- успешная лента;
- пустой кэш;
- ошибка загрузки;
- обновление текущей ленты;
- неактивные действия с отсутствующей резервной копией;
- выполнение операции с копией.

Для форм и настроек есть ошибки отдельных полей, общая ошибка и подтверждение
заменяющих действий. Обратная связь реализована через `supportingText`,
`Snackbar`, `CircularProgressIndicator` и `AlertDialog`. Ошибка всегда имеет
текст, а не только цвет.

### 2.10. Валидация как доменная логика

`Validation` не зависит от Android и возвращает `ValidationResult.Valid` или
`ValidationResult.Invalid(message)`.

Проверяются:

- имя — 2–40 символов после `trim()`;
- логин — 3–64 символа;
- формат e-mail, если логин содержит `@`;
- пароль — 6–64 символа;
- совпадение пароля и подтверждения;
- возраст — 6–120 лет.

Правила:

- одна функция проверяет одно правило;
- ошибки показываются рядом с полем;
- неудачный вход не стирает логин;
- регистрация проверяется до сохранения аккаунта;
- настройки профиля используют ту же domain-валидацию.

### 2.11. Типизированная навигация

Межэкранные результаты описаны через `ActivityResultContract`:

- `RegistrationContract` возвращает логин после регистрации;
- `SettingsContract` возвращает логин и признак изменения профиля.

Это исключает глобальные переменные и передачу пароля или полного профиля через
`Intent`. Контракт явно обрабатывает `RESULT_OK` и отсутствие результата.

### 2.12. Управление стеком Activity

```text
StartActivity -> RegistrationActivity -> StartActivity
StartActivity -> ContentActivity -> SettingsActivity -> ContentActivity
```

Использованы практики:

- после входа `StartActivity` вызывает `finish()`;
- после регистрации `RegistrationActivity` возвращает результат и закрывается;
- `SettingsActivity` возвращает результат в `ContentActivity`;
- системная кнопка «Назад» в настройках возвращает к ленте;
- повторный переход блокируется флагом, чтобы не открыть дубликат Activity;
- выход из `ContentActivity` подтверждается `AlertDialog`.

### 2.13. Загрузка JokeAPI и дедупликация

JokeAPI используется как основной сетевой источник шуток. Репозиторий
запрашивает endpoint:

```text
https://v2.jokeapi.dev/joke/Any?type=twopart&amount=10&safe-mode&lang=en
```

Запросы идут пакетами, потому что API ограничивает `amount` десятью шутками.
Алгоритм:

1. выполнить запрос до 10 шуток;
2. преобразовать пакет в `List<JokeCard>`;
3. сложить шутки в `LinkedHashMap<Int, JokeCard>` по `id`;
4. повторить запрос, пока не собрано 12 уникальных шуток или не исчерпано три
   попытки;
5. ограничить итог двадцатью шутками;
6. сохранить результат в кэш.

Сохранение порядка через `LinkedHashMap` даёт стабильный порядок карточек.
Неизвестные категории и типы API маппятся в `UNKNOWN` без падения.

### 2.14. Проверка и безопасность сетевого контента

Запрос использует `safe-mode`, чтобы снизить вероятность нежелательного
контента. Ответ проверяется на `error: true`; HTTP-статус вне диапазона
`200..299` считается ошибкой. Текст и `id` шутки обязательны, а запрос имеет
ограниченные таймауты.

Это учебное приложение не заменяет модерацию контента: базовый режим JokeAPI не
гарантирует отсутствие всего спорного материала. Тексты API показываются в
исходном виде и не выполняются как разметка или код.

### 2.15. JSON-кодек и преобразование DTO

`JokeJsonCodec` выполняет две задачи:

1. разбирает одиночный или пакетный ответ JokeAPI;
2. сериализует и восстанавливает локальный кэш и резервную копию.

Поддерживаются:

- `single` с полем `joke` и отсутствующим панчлайном;
- `twopart` с полями `setup` и `delivery`;
- поле `id`, `category`, `safe`, `lang`;
- вычисление количества слов;
- `error: false` и `error: true`.

Неполные или некорректные объекты отклоняются с понятной ошибкой. В UI и
ViewModel не передаются `JSONObject`, `JSONArray` или HTTP-ответ.

### 2.16. Кэш и атомарная запись

| Данные | Место |
|---|---|
| Профиль, соль и хеш | `SharedPreferences` `punchline_user` |
| Тема и масштаб | `SharedPreferences` `punchline_settings` |
| Инициализация кэша | `SharedPreferences` `joke_cache_state` |
| Кэш ленты | `filesDir/jokes_cache.json` |
| Резервная копия | `filesDir/backup/jokes_backup.json` |

Кэш содержит версию, источник и `jokes`. Копия версии 2 содержит версию, дату и
`jokes`.

```json
{
  "version": 2,
  "createdAt": "2026-10-25T12:00:00+03:00",
  "jokes": []
}
```

И кэш, и копия сначала записываются во временный файл. После проверки временный
файл заменяет целевой через предыдущую версию. Исходные данные не должны
зависеть от неудачной записи. При повреждённом JSON кэш не перезаписывается, а
операция возвращает ошибку.

### 2.17. Работа с ошибками сети и файлов

Ошибки API, меньше 12 уникальных шуток, HTTP-статусы и повреждённый JSON
преобразуются в сообщения пользователю. Если обновление не удалось, приложение
не должно стирать уже сохранённый кэш. Для повторной попытки есть кнопка
«Повторить».

Ошибки файлов обрабатываются через `runCatching` и сообщения операций.
Приложение не завершается из-за сетевой ошибки, таймаута или отсутствия
копии.

### 2.18. Безопасность пароля

`PasswordHasher` создаёт уникальную случайную соль и вычисляет HMAC-SHA256 с
итерациями. В `SharedPreferences` хранятся только соль и хеш в Base64. При
проверке используется сравнение в постоянном времени.

Открытый пароль:

- не пишется в файл;
- не передаётся через `Intent`;
- не выводится в Logcat;
- очищается в `CharArray` после использования.

Это учебная локальная аутентификация, а не замена серверной авторизации.

### 2.19. Локализация и доступность

Пользовательские строки русскоязычного UI находятся в `strings.xml` и читаются
через `stringResource`. Для счётчиков и сообщений используются строковые
шаблоны. Названия и тексты шуток JokeAPI приходят на английском и отображаются
без искажения.

Элементы доступности:

- у графического значка шутки есть `contentDescription` с категорией;
- кнопки имеют текстовую подпись или семантическое описание;
- категория и safe-mode выражаются не только цветом;
- поля ввода имеют label и текст ошибки;
- основные элементы имеют область нажатия около 48 dp.

### 2.20. Тестирование

JUnit-тесты domain не требуют Android-эмулятора. `JokeFeedPolicyTest`
проверяет:

- дедупликацию по API `id` с сохранением первой версии шутки;
- верхнюю границу коллекции в 20 карточек;
- объединение нескольких пакетов до минимального размера 12 шуток.

`ValidationTest` проверяет границы имени, логина, пароля и возраста. Compose
UI-тесты не добавлены, поэтому проверка интерфейса выполняется вручную или на
устройстве. Разбор JSON выполняется Android-реализацией `org.json`, поэтому его
интеграционная проверка требует устройства или эмулятора.

### 2.21. Ресурсы приложения

Логотип, фон и категорийные значки рисуются локально в Compose. JokeAPI не
предоставляет изображений для карточек, поэтому сетевой загрузки иллюстраций нет.
Текстовый контент остаётся основным носителем смысла, а графический значок —
дополнительным.

### 2.22. Защита от повторных действий

- `isSubmitting` блокирует повторную регистрацию и вход;
- `isLoading` блокирует повторное обновление и операции с копией;
- `navigating` не позволяет открыть `ContentActivity` дважды после входа;
- `settingsOpen` предотвращает два параллельных перехода в настройки;
- диалоги подтверждения отделяют намерение от записи файла.

## 3. Отличительные черты

### 3.1. Сетевой источник с офлайн-кэшем

UI зависит от `JokeRepository`, а не от JokeAPI. `RemoteJokeRepository`
объединяет пакетную загрузку, дедупликацию, проверку ошибок, маппинг JSON и
атомарный кэш. Если API недоступен, ранее загруженная коллекция остаётся
сохранённой в кэше.

### 3.2. Двухшаговый сценарий восстановления

Пользователю показаны два уровня сохранения данных:

- автоматический кэш успешной загрузки;
- явная резервная копия для восстановления после очистки кэша.

Это позволяет отдельно проверить сетевую загрузку и офлайн-восстановление.

### 3.3. Собственный визуальный язык Punchline

- логотип улыбающегося смайла, нарисованный локально;
- градиентный фон и карточки с крупными скруглениями;
- цветовое кодирование категорий шуток;
- текстовый бейдж `Safe mode`;
- отдельный визуальный блок панчлайна;
- русскоязычная навигация вокруг англоязычного контента API.

### 3.4. Проверяемые состояния копии

Сценарий:

```text
загрузить шутки -> создать копию -> очистить кэш
-> восстановить копию -> удалить копию
```

Пустая лента предлагает восстановить копию или открыть настройки и не оставляет
пользователя на тупиковом экране.

## 5. Ограничения текущей реализации

- нет серверной авторизации, OAuth или JWT;
- аккаунт один на устройство;
- JokeAPI не поддерживает полноценную пагинацию коллекции, поэтому пакеты
  объединяются до нужного размера;
- `safe-mode` не заменяет ручную модерацию контента;
- тексты API не переводятся на русский;
- поиск и фильтрация по категориям не обязательны в этой версии;
- нет Compose UI-тестов и проверки реального API в автоматическом CI;
- JSON-кэш и копия не шифруются, но находятся в приватном `filesDir`.

## 6. Возможные ошибки и их причины

1. **JokeAPI недоступен.** Проверьте интернет, DNS и таймауты. При наличии
   кэша показывайте сохранённые шутки, а не пустой экран.
2. **Меньше 12 уникальных шуток.** API может вернуть пересекающиеся `id` в
   пакетах. Репозиторий повторяет запрос и затем сообщает об ошибке.
3. **Повреждённый JSON-кэш.** Чтение возвращает ошибку, рабочий файл не
   перезаписывается; пользователь может восстановить явную копию.
4. **Неизвестная категория API.** Она маппится в `UNKNOWN`, карточка остаётся
   читаемой.
5. **Ошибка записи копии.** Показывается `Snackbar`; предыдущая копия по
   возможности не удаляется до успешной замены.
6. **Сеть требуется на первом запуске.** Без соединения и кэша пользователь
   увидит ошибку и кнопку повторной загрузки.
7. **Доступность.** Не у всех пиктограмм и кнопок «Назад» есть семантические
   подписи; это направление для улучшения.
8. **Тексты JokeAPI.** API отдаёт контент на английском; локализация шуток не
   входит в задание.

## 7. Итоговая характеристика

`Punchline` — Android-приложение коллекции шуток на Kotlin и Jetpack Compose с
четырьмя Activity. Оно загружает данные JokeAPI пакетами, проверяет ответ и
дедуплицирует шутки, сохраняет успешный результат в JSON-кэш и показывает его
через MVVM-состояние. Локальная авторизация использует хеширование с солью:
пароль не передаётся между Activity и не пишется в логи. Настройки оформления и
резервная копия шуток сохраняются на устройстве. Unit-тесты покрывают границы
валидации и разбор основных форматов JokeAPI.
