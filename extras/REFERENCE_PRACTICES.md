включена поддержка Compose, но боевые экраны используют XML-разметку.

## Краткая карта решения

| Область | Фактически используется |
|---|---|
| Язык | Kotlin |
| UI | Android Views, XML, Material Components / Material 3 |
| Список | `RecyclerView`, `GridLayoutManager`, собственные `Adapter` и `ViewHolder` |
| Экраны | четыре `AppCompatActivity`: старт, регистрация, рецепты, настройки |
| Навигация | явные `Intent`; запуск регистрации через Activity Result API |
| Профиль | `SharedPreferences` с именем файла `user_prefs`, режим `MODE_PRIVATE` |
| Пароль | открытая строка в `SharedPreferences` и `Intent` |
| Рецепты | статический список в памяти `ContentActivity` |
| Резервная копия | текстовый файл `filesDir/backup.txt` |
| Сеть | отсутствует |
| База данных | отсутствует |
| Асинхронность | корутины, `Flow`, `LiveData` и фоновые потоки не используются |
| Архитектурное разделение | минимальное: Activity напрямую работает с UI и данными |
| Сборка | Gradle Kotlin DSL и version catalog |
| Логи | расширение `debugging()`, тег `TAG_<Activity>` |

## Удачные практики, которые можно взять за образец

### 1. Явная навигация между небольшими экранами

Каждый крупный сценарий вынесен в отдельную Activity:

```text
StartActivity
  ├── RegistrationActivity (запрос результата)
  └── ContentActivity
        └── SettingsActivity
```

Переходы выполняются явными `Intent(this, NextActivity::class.java)`, поэтому
целевой экран виден в коде. После входа `StartActivity` закрывается через
`finish()`, чтобы экран входа не оставался в стеке под контентом.

Это хороший ориентир для простого учебного приложения с небольшим числом
экранов. Для более крупного приложения эталоном будет Single-Activity и
Navigation Compose или Navigation Component.

### 2. Современный запуск Activity за результатом

Регистрация запускается через `registerForActivityResult(...)` и
`ActivityResultLauncher`, а не через устаревший `startActivityForResult`.
Результат возвращается через `setResult(RESULT_OK, intent)` и `finish()`.

Эталонный приём здесь — явная передача результата регистрации обратно на
стартовый экран и обработка только успешного результата. Способ передачи самих
данных требует исправления, см. раздел ограничений.

### 3. XML-интерфейс на Material Components

Разметка использует:

- `TextInputLayout` и `TextInputEditText` вместо обычных полей ввода;
- `MaterialToolbar`, `MaterialCardView`, `MaterialButtonToggleGroup`,
  `MaterialSwitch`, `Slider` и `Snackbar`;
- `ScrollView` с `fillViewport` для форм, которые могут не поместиться на
  небольшом экране;
- `CoordinatorLayout` и `AppBarLayout` для экрана контента;
- `RecyclerView` с `GridLayoutManager` для сетки карточек;
- отдельную разметку `item_meal.xml` для элемента списка;
- локальные drawable и mipmap-ресурсы для логотипа и карточек.

Это последовательное применение Material-компонентов и ресурсов Android
вместо ручного создания всех View в Kotlin-коде.

### 4. Обработка edge-to-edge и системных отступов

На экранах вызывается `enableEdgeToEdge()`, а затем через
`ViewCompat.setOnApplyWindowInsetsListener(...)` из `WindowInsetsCompat`
извлекаются отступы системных панелей и применяются к корневому View. Это
корректный базовый пример современного edge-to-edge без перекрытия контента
статус-баром и навигационной панелью.

### 5. Разделение списка на адаптер и модель

`Meal` — отдельная неизменяемая `data class` с идентификатором, названием,
ресурсом изображения, категорией, кухней и временем приготовления.

`MealAdapter` отвечает за:

- создание View через `LayoutInflater` в `onCreateViewHolder`;
- привязку данных в `onBindViewHolder`;
- повторное использование `ViewHolder`;
- передачу выбранной модели через лямбду `onMealClick`.

`ContentActivity` отвечает за источник данных, менеджер раскладки, пагинацию и
показ сообщения по клику. Это хорошее разделение обязанностей в пределах
классического RecyclerView-подхода.

### 6. Пагинация по размеру страницы

Список рецептов делится на страницы по 10 элементов. Код хранит
`visibleCount`, увеличивает его с ограничением
`coerceAtMost(allMeals.size)` и передаёт в адаптер срез
`allMeals.take(visibleCount)`. После показа последней страницы кнопка
«Загрузить ещё» скрывается.

Полезные элементы практики:

- отдельные именованные константы и счётчики вместо магических чисел в
  обработчике;
- `coerceAtMost` не позволяет счётчику выйти за границу;
- видимость кнопки зависит от достижения конца списка.

Это пагинация на уже загруженной коллекции, а не сетевая подгрузка. Для
production-ленты понадобятся Paging, состояния загрузки и восстановление
состояния после пересоздания Activity.

### 7. Явные состояния контента

В экране рецептов предусмотрены отдельные View для успешного списка,
загрузки и пустого состояния. Методы `showSuccess()`, `showEmpty()` и
`loadMore()` централизуют переключение видимости. В XML для пустого состояния
есть текст и действие восстановления.

Эталонная идея — не смешивать список, пустое состояние и индикатор загрузки в
одном наборе случайных условий. Однако в текущей реализации `showLoading()`
отсутствует, а `state_loading` фактически не включается. В полноценной
реализации состояния лучше выражать одной моделью UI-state.

### 8. Валидация перед сохранением

Проверки выполняются до возврата результата или записи настроек:

- логин должен содержать `@`;
- пароль должен быть не короче шести символов;
- пароль и подтверждение должны совпадать;
- имя не должно быть пустым;
- в настройках возраст должен быть больше нуля и не больше 120.

Пользователь получает текстовую обратную связь через `Snackbar`, а при ошибке
действие не продолжается. Принцип «сначала проверить, затем сохранить» правильный.
Сами правила упрощены; production-валидация должна также показывать ошибки
непосредственно около полей и проверять полный формат адреса почты.

### 9. Пользовательская обратная связь через Snackbar

`Snackbar` используется для ошибок входа, ошибок валидации, результата
сохранения профиля и результата операций с резервной копией. Сообщения
привязаны к корневому View экрана, поэтому не блокируют интерфейс модальным
диалогом.

Это эталонный минимальный способ дать пользователю краткую обратную связь. Для
необратимых операций, например удаления, в качественном приложении следует
добавить подтверждение.

### 10. Локальное хранение простых настроек через SharedPreferences

Для небольшого набора скалярных значений используется именованный файл
`user_prefs` с режимом `MODE_PRIVATE`. Значения читаются через `getString`,
`getInt` и `getBoolean`, а записываются одной транзакцией `edit().put...apply()`.

Здесь есть правильные практики:

- настройки пользователя не передаются между Activity без необходимости, а
  читаются из одного локального источника;
- запись нескольких полей объединена в один `edit()`;
- используется `apply()` для асинхронной записи из UI-потока;
- настройки применяются к элементам формы при открытии экрана.

`SharedPreferences` подходит для небольших флагов и простых настроек. Для
профиля, секретов и структурированных данных эталоном являются DataStore,
Room и Android Keystore соответственно.

### 11. Светлая и тёмная темы

Есть `values/themes.xml` и `values-night/themes.xml`. Переключение темы
описано через `AppCompatDelegate.setDefaultNightMode(...)`, а выбранный режим
сохраняется в `SharedPreferences`. Для масштаба шрифта сохраняется число и
настройка применяется после завершения перемещения `Slider`.

Это демонстрирует правильную основу темизации через системный ночной режим и
ресурсы конфигурации. Для законченной практики нужно подключить обработчик
`MaterialSwitch` и фактически применять сохранённый масштаб шрифта во всех
экранах.

### 12. Логирование жизненного цикла через расширение

Функция `AppCompatActivity.debugging(message)` пишет через `Log.d` и добавляет
к тегу имя текущей Activity. Это уменьшает дублирование и позволяет различать
события экранов в Logcat.

Для учебной демонстрации это удобно. В production-варианте нужен `BuildConfig`
или отдельный флаг release/debug и логирование всех требуемых методов
жизненного цикла, а не только нескольких пользовательских действий.

### 13. Явные экспортируемые компоненты

В манифесте launcher Activity объявлена с `android:exported="true"`, а
регистрация, контент и настройки — с `android:exported="false"`. Это эталонная
базовая настройка поверхности приложения: снаружи доступен только нужный вход,
остальные Activity не открываются сторонними приложениями.

### 14. Kotlin DSL и version catalog

Сборка использует `build.gradle.kts`, `settings.gradle.kts` и
`gradle/libs.versions.toml`. Версии зависимостей и плагинов вынесены в
каталог версий и подключаются через `alias(...)`. Это уменьшает разрозненные
версии и делает зависимости обозримыми.

### 15. Управление возвратом из настроек

Для возврата в рецепты используется явный `Intent` с
`Intent.FLAG_ACTIVITY_CLEAR_TOP`, затем текущая Activity закрывается через
`finish()`. Кнопка toolbar и кнопка в контенте ведут к одинаковому методу
навигации.

Идея централизовать возврат в одном методе правильная. Однако сочетание
`CLEAR_TOP` с отдельным `ContentActivity` и `finish()` следует проверить на
реальном сценарии back stack, чтобы не создавать лишние экземпляры.

## Как хранятся данные

### Профиль и настройки

Используется один `SharedPreferences`-файл `user_prefs` со следующими ключами:

| Ключ | Значение | Когда используется |
|---|---|---|
| `LOGIN` | строка логина/e-mail | после регистрации |
| `NAME` | имя пользователя | регистрация, настройки |
| `GENDER` | `Boolean`: `true` — Mr., `false` — Mrs. | регистрация, настройки |
| `PASSWORD` | пароль в открытом виде | запись после регистрации и проверка входа |
| `AGE` | возраст | экран настроек |
| `DARK_THEME` | выбранный ночной режим | метод темы |
| `FONT_SIZE` | выбранный размер шрифта | метод масштаба |

Запись профиля выполняется из `StartActivity.useResult()` после успешной
регистрации. Настройки профиля и темы дополнительно сохраняются из
`SettingsActivity`. Режим `MODE_PRIVATE` ограничивает доступ других приложений
к preferences обычными средствами Android, но не защищает секреты на
скомпрометированном устройстве.

### Список рецептов

Список из 20 элементов создаётся методом `ContentActivity.loadMeals()` и
хранится в изменяемом `MutableList<Meal>` в памяти Activity. Элементы не
читаются из сети, базы или файла. Все карточки используют один и тот же
ресурс `R.mipmap.ic_launcher` в качестве изображения.

Из-за того что коллекция создаётся в `onCreate`, она не является
долговременным хранилищем. После пересоздания Activity создаётся заново, а
пользовательские изменения в неё не записываются.

### Резервная копия

Копия записывается в приватный внутренний файл:

```text
filesDir/backup.txt
```

Метод `createBackup()` записывает фиксированную строку
`Meal1,Meal2,Meal3,Meal4,Meal5`, а не текущий список рецептов. Удаление
проверяет наличие файла и вызывает `File.delete()`. Восстановление читает
содержимое и показывает его в `Snackbar`, но не заменяет список рецептов.

Таким образом, это демонстрация файлового ввода-вывода, а не полноценное
резервное копирование доменных данных. Файл находится во внутреннем хранилище
и использует `openFileOutput(..., MODE_PRIVATE)` / `openFileInput(...)`, поэтому
обычные сторонние приложения не имеют к нему прямого доступа.

### Ресурсы

Иконки, drawable и mipmap хранятся в `src/main/res`. Строки в большей части
разметки заданы литералами прямо в XML или Kotlin; локализация через отдельный
`strings.xml` фактически не проведена. Это учебное упрощение, а не эталонная
практика интернационализации.

## Как передаются данные

### Из регистрации на старт

`RegistrationActivity` записывает в результат `Intent` четыре extras:

```kotlin
LOGIN     -> loginText
GENDER    -> Boolean
NAME      -> nameText
PASSWORD  -> passwordText
```

Далее `StartActivity` получает `Intent` в Activity Result callback, извлекает
значения и сохраняет их в `SharedPreferences`. Передача пароля через `Intent`
является существенным недостатком: extras могут попасть в диагностические
средства или быть сохранены системой вместе с состоянием задачи. Для
production-приложения передавать пароль между Activity не следует.

### Между контентом и настройками

`ContentActivity` открывает `SettingsActivity` явным `Intent` без
дополнительных данных. `SettingsActivity` сама читает профиль из
`SharedPreferences` и записывает изменения туда же. Это лучше, чем передавать
весь профиль через extras, потому что экран настроек получает данные из
общего локального источника.

### Внутри экрана рецептов

От `ContentActivity` в `MealAdapter` передаётся лямбда-обработчик клика. При
нажатии адаптер передаёт lambda объект `Meal`, а Activity показывает имя
выбранного рецепта через `Snackbar`. Это типобезопасная передача события без
явных extras и глобальных переменных.

### Сводная схема

```text
RegistrationActivity ──result Intent: LOGIN/NAME/GENDER/PASSWORD──▶ StartActivity
                                                                    │
                                                                    ▼
                                                         SharedPreferences(user_prefs)
                                                                    ▲
                                                                    │
ContentActivity ─────────────Intent без extras──────────────▶ SettingsActivity
       │
       └── List<Meal> ──адаптер──▶ карточки ──клик──▶ Snackbar

SettingsActivity ──openFileOutput/readText──▶ filesDir/backup.txt
```

## Ограничения: не переносить без исправления

### Безопасность

1. **Пароль хранится в открытом виде.** Ключ `PASSWORD` записывается в
   `SharedPreferences`, а вход сравнивает введённую строку с сохранённой.
   Эталон: хешировать пароль с солью и достаточной вычислительной стоимостью,
   а для ключей использовать Android Keystore. Это учебное приложение не
   должно считаться образцом аутентификации.
2. **Пароль передаётся через `Intent` extras.** Эталон: не передавать секреты
   между Activity; проверять/хешировать пароль внутри слоя аутентификации и
   передавать только безопасный идентификатор или результат операции.
3. **Персональные данные разрешено включать в системный backup.**
   `android:allowBackup="true"` и файлы правил backup присутствуют. Для
   секретов и приватных данных нужен явный анализ правил исключения и
   шифрования.
4. **`DEBUG` константа всегда `true`.** Логи могут попасть в release-сборку.
   Эталон: отключать подробные логи в release и не логировать персональные
   данные или пароли.
5. **В `Snackbar` выводится `e.message`.** Внутренние сообщения исключений
   могут раскрывать детали реализации. Эталон: логировать техническую причину
   отдельно, а пользователю показывать понятное безопасное сообщение.

### Архитектура и данные

1. Activity напрямую выполняет валидацию, хранение, файловые операции и
   навигацию. Отсутствуют ViewModel, репозитории, use case и DI. Для
   лабораторной Views-подхода это допустимо, но не эталон масштабируемой
   архитектуры.
2. Список рецептов и счётчик пагинации не сохраняются через
   `onSaveInstanceState`. При пересоздании Activity пользователь теряет
   прокрутку и количество показанных элементов, если эти свойства не
   восстанавливаются другим способом.
3. `notifyDataSetChanged()` обновляет весь список. Эталон для production:
   `ListAdapter` + `DiffUtil` или другой механизм точечных изменений.
4. `submitList()` получает неизменяемый `List<Meal>`, но сам адаптер не хранит
   стабильные ID и не реализует diff-логику. Для карточек с повторным
   использованием View это стоит улучшить.
5. `stateLoading` присутствует в XML, но не управляется отдельным методом и
   фактически не показывается. Состояния интерфейса не выражены единым
   источником истины.
6. `showEmpty()` вызывается только после синхронного заполнения фиксированного
   списка, поэтому пустого состояния в текущем сценарии не будет. Ветка не
   проверяет реальный источник данных.
7. Фиктивное поле «рейтинг» вычисляется как
   `cookingTime % 10`, а не загружается как рейтинг. Время, рейтинг, кухня и
   картинка — демонстрационные данные. Нельзя считать это моделью реального
   API.
8. Нет сетевого слоя, API-клиента, DTO, сериализации, кэша и обработки сетевых
   ошибок. Название `ContentActivity` не означает, что данные приходят из
   внешнего источника.
9. Нет `Room`, DataStore, корутин и `Flow`. Файловое чтение и запись в
   `SettingsActivity` выполняются синхронно в UI-потоке. Для реальных объёмов
   данных и медленного хранилища эталон — suspend-операции и
   `Dispatchers.IO`.
10. Резервная копия содержит фиксированную строку, а восстановление только
    показывает её. Нет сериализации текущего списка, валидации формата,
    версии формата, атомарной замены файла и обработки ошибок восстановления
    на уровне данных.

### UI и UX

1. Тёмный переключатель `switch_theme` присутствует в разметке, но в
   `SettingsActivity` ему не назначен обработчик изменения. Метод
   `applyTheme()` существует, однако не вызывается из текущего UI.
2. Выбранный `FONT_SIZE` сохраняется, но не применяется к тексту экранов.
   Сохранение значения без фактического применения не является завершённой
   функцией.
3. Основной текст и подписи в layout заданы литералами. Для локализации,
   единообразия и тестирования эталонно использовать `strings.xml` и
   `stringResource`/`getString`.
4. В коде встречаются смешанные языки интерфейса: русские сообщения и
   английские подписи/уведомления. Это не эталон пользовательского опыта.
5. Удаление резервной копии не подтверждается диалогом и не обрабатывает
   результат `delete()`; операцию нельзя отменить.
6. После ошибки пользователь получает `Snackbar`, но поля не получают
   `TextInputLayout.error`, фокус не переводится, а повторный ввод не
   подсвечивается. Для эталонной формы валидации стоит показывать ошибку около
   конкретного поля.
7. В `StartActivity` есть два пути в контент: обычный вход и отдельная кнопка
   `btn_go_to_recipes`, которая запускает `ContentActivity` без проверки
   введённых данных. Поэтому проверка пароля не защищает весь путь доступа.

### Проверки и сборка

1. Unit- и instrumented-тесты являются стандартными заготовками шаблона и не
   проверяют сценарии приложения. Эталон: тесты валидации, навигационных
   результатов, адаптера, пагинации и восстановления данных.
2. `compileSdk 37` и `targetSdk 37` в анализируемой конфигурации следует
   проверить на соответствие требованиям курса и установленной Android Studio;
   при несовпадении проект может не собраться в окружении преподавателя.
3. Compose-зависимости и `MainActivity` с Compose-шаблоном добавлены, но
   `MainActivity` не объявлена в манифесте и не участвует в сценарии. Смешение
   двух UI-подходов увеличивает неиспользуемую поверхность проекта.
4. Оптимизация release-сборки отключена (`optimization.enable = false`).
   Это не эталон production-конфигурации и требует отдельного объяснения для
   учебного задания.

## Итоговая оценка

В `first_lab` есть хорошие базовые Android-практики: Material Views, явные
Activity-переходы, Activity Result API, RecyclerView с ViewHolder, edge-to-edge,
приватные preferences для простых настроек, адаптивная темизация, версионируемый
Gradle-каталог и наглядная обработка ошибок. Их можно использовать как
эталонные примеры для первого знакомства с Android Views.

При этом проект нельзя считать эталоном архитектуры или безопасности:
авторизация хранит пароль открыто, ключевые данные живут в Activity, списки и
резервные копии демонстрационные, а тесты не проверяют бизнес-сценарии. В
следующей версии эталонными будут ViewModel + StateFlow, отдельный слой
репозитория, DataStore/Room, безопасное хеширование пароля, строковые ресурсы,
DiffUtil и реальные тесты.
